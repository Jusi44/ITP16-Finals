## Schema Design

### Enums

- `user_role`: `ADMIN`, `STAFF`.
- `stock_type`: `RESTOCK`, `SALE`.

### `users`

- `id uuid PK DEFAULT gen_random_uuid()`.
- `username citext UNIQUE NOT NULL` — Drizzle has no built-in citext column in 0.45.4, so a `customType<{ data: string }>` returning `citext` is used. This makes usernames case-insensitively unique.
- `password_hash text NOT NULL`.
- `role user_role NOT NULL DEFAULT 'STAFF'`.
- `created_at timestamptz NOT NULL DEFAULT now()`.

### `food_items`

- `id uuid PK DEFAULT gen_random_uuid()`.
- `name text NOT NULL`, `category text NOT NULL`.
- `price numeric(12,2) NOT NULL CHECK (price >= 0)`.
- `current_stock int NOT NULL DEFAULT 0 CHECK (current_stock >= 0)`.
- `min_threshold int NOT NULL DEFAULT 5 CHECK (min_threshold >= 0)`.
- `created_at timestamptz NOT NULL DEFAULT now()`.
- `updated_at timestamptz NOT NULL DEFAULT now()`.

### `sales`

- `id uuid PK DEFAULT gen_random_uuid()`.
- `item_id uuid REFERENCES food_items(id) ON DELETE SET NULL` (nullable).
- `item_name text NOT NULL` — immutable snapshot.
- `quantity_sold int NOT NULL CHECK (quantity_sold > 0)`.
- `total_price numeric(12,2) NOT NULL`.
- `user_id uuid REFERENCES users(id) ON DELETE SET NULL` (nullable).
- `username text NOT NULL` — snapshot.
- `created_at timestamptz NOT NULL DEFAULT now()`.

### `stock_records`

- `id uuid PK DEFAULT gen_random_uuid()`.
- `item_id uuid REFERENCES food_items(id) ON DELETE SET NULL` (nullable).
- `item_name text NOT NULL` — snapshot.
- `quantity_changed int NOT NULL CHECK (quantity_changed > 0)` — positive magnitude; the UI derives `+N`/`-N` from `type`.
- `type stock_type NOT NULL`.
- `user_id uuid REFERENCES users(id) ON DELETE SET NULL` (nullable).
- `username text NOT NULL DEFAULT 'System'`.
- `created_at timestamptz NOT NULL DEFAULT now()`.

### `sessions`

- `id uuid PK DEFAULT gen_random_uuid()`.
- `user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE`.
- `token_hash text UNIQUE NOT NULL`.
- `expires_at timestamptz NOT NULL`.
- `created_at timestamptz NOT NULL DEFAULT now()`.

### Indexes

- `sales_created_at_idx` on `sales (created_at DESC)`.
- `stock_records_created_at_idx` on `stock_records (created_at DESC)`.
- `stock_records_item_id_idx` on `stock_records (item_id)`.
- `sessions_expires_at_idx` on `sessions (expires_at)`.
- `sessions_user_id_idx` on `sessions (user_id)`.
- Unique indexes/constraints on `users.username` and `sessions.token_hash` come from `.unique()`.

### `updated_at` maintenance

- A forward-only custom migration creates:
  - `set_updated_at()` as a `plpgsql` trigger function that assigns `NEW.updated_at = now()`.
  - `food_items_set_updated_at` as a `BEFORE UPDATE ... FOR EACH ROW` trigger on `food_items`.
- Rejected: Drizzle's `$onUpdate()` only runs through the ORM, so raw SQL or ops scripts would leave `updated_at` stale.
- Drizzle schema still declares the column with `defaultNow()`; the trigger handles updates.

## Money Handling

- All money columns stay `numeric(12,2)` and are typed as `string` in TypeScript.
- Drizzle's default `numeric` mode returns strings. We do **not** use `mode: 'number'` and never call `parseFloat`/`Number` on money.
- `db/src/money.ts` exports `MoneyString` and a strict decimal-string validator for inserts/updates and Phase 2 Zod schemas.
- Seed fixtures pass strings such as `'65.00'`.
- In Phase 2, sale totals and report sums are computed in SQL (`price * quantity`, `sum(total_price)`) and returned/cast as decimal strings. The UI formats them with `Intl.NumberFormat` (Phase 3).
- No JS float arithmetic is used for totals, refunds, or reporting.

## Seed Scripts

### `db/src/seed.ts`

- Reads `SEED_ADMIN_PASSWORD` and `SEED_STAFF_PASSWORD` from the environment (root `.env` locally).
- Refuses to run if either is missing, empty, shorter than 8, longer than 128, or a known placeholder (`local_dev_only_change_me`, `change_me`, `password`, etc.).
- Hashes with argon2id via `@node-rs/argon2` (`Algorithm.Argon2id`, memory 19456 KiB, time 2, parallelism 1).
- Inserts `admin` / `ADMIN` and `staff` / `STAFF` in one transaction.
- Idempotent: `INSERT ... ON CONFLICT (username) DO NOTHING`. Existing users are skipped and their passwords are **not** overwritten. Running twice leaves exactly two users and unchanged hashes.
- Never logs passwords or hashes.
- Production use is allowed only with explicit seed env vars (Phase 8).

### `db/src/seed-sample-items.ts`

- Refuses to run when `NODE_ENV=production`.
- Inserts a small dev-only menu, skipping items whose name already exists case-insensitively:
  - Chicken Adobo Rice (Meals, 65.00, stock 20, threshold 5)
  - Pancit Bihon (Meals, 50.00, stock 4, threshold 5 — low)
  - Iced Tea (Drinks, 25.00, stock 30, threshold 5)
  - Bottled Water (Drinks, 20.00, stock 0, threshold 5 — out of stock)
  - Banana Chips (Snacks, 15.00, stock 40, threshold 5)
  - Leche Flan (Desserts, 35.00, stock 3, threshold 5 — low)
- Prices are decimal strings. The seed is safe to run twice.

### Password rotation

- `db/src/set-password.ts`, plus `db/src/hidden-prompt.ts`.
- Reads the username from `SET_PASSWORD_USER` or prompts.
- Reads the new password from `SET_PASSWORD` or a hidden raw-mode prompt. It never accepts the password as a command-line argument, never echoes it, and never logs it or its hash.
- Validates 8-128 characters and that the user exists.
- Updates `password_hash` and deletes all sessions for that user in the same transaction, so rotation revokes existing logins.
- Output is limited to `Password updated for <username>`.
- Dev command: `npm run user:set-password -w api`; compiled command for ops: `node db/dist/set-password.js`.

## Environment and Secrets (Phase 0 follow-up 1)

- `SESSION_SECRET` is **not used** and will be removed from `.env.example`, `README.md`, and any env parsing.
- Sessions are 256-bit random opaque tokens. The DB stores only `SHA-256(token)`, which is an unkeyed hash; login verifies by hashing the presented cookie and looking up the row. There is nothing to sign and no secret to keep. Adding an HMAC pepper would change the approved SHA-256 scheme, so it is rejected.
- `api/src/env.ts` will fail at startup when `NODE_ENV=production` and:
  - `DATABASE_URL` is missing, uses the wrong protocol, contains a placeholder (`local_dev_only`, `change_me`, `replace_`, `example`, `localhost`, `127.0.0.1`), or has an empty/short password.
  - `APP_TIMEZONE` is not a valid IANA zone.
  - `TRUST_PROXY` is `false` (CloudFront/ALB deployment must trust the configured proxy CIDRs).
- Seed secrets are validated by the seed scripts, not by the API process.
- Secure-cookie and `__Host-` prefix enforcement remains a Phase 2 auth concern; Phase 1 only prepares the session table.

- It does not touch `drizzle.__drizzle_migrations`.
- Tests run serially (`fileParallelism: false`, `maxWorkers: 1`) and call the helper in `beforeEach`.

### Tests

- **Stock cannot go negative:** insert an item at stock 0, attempt `UPDATE food_items SET current_stock = -1`; expect Postgres error `23514` from the CHECK constraint. This is the DB-level proof.
- Also cover: negative price, zero/negative `quantity_sold`, zero/negative `quantity_changed`, case-insensitive duplicate usernames (`23505`), session cascade deletion when a user is deleted, `sales.item_id` becoming null while `item_name` survives, and the `updated_at` trigger.

- **Sample seed:** refuses when `NODE_ENV=production`, and is idempotent locally.
- **Password rotation:** updates the hash, verifies the new password, revokes all sessions, and rejects invalid lengths.

## Key Decisions and Rejected Alternatives

1. **Custom `citext` column type** — Drizzle 0.45.4 has no built-in citext; a `customType` with `dataType() => 'citext'` is used. Rejected: `text` + `lower()` unique index, which would not match the approved schema.
2. **DB trigger for `updated_at`** — guarantees correctness for ORM and raw SQL. Rejected: Drizzle `$onUpdate()`.
3. **`migrate()` from `drizzle-orm` for production** — compiled JS runs with only `pg`/`drizzle-orm`. Rejected: `drizzle-kit migrate` in production, which would require a dev dependency and `tsx`.
4. **Decimal strings** — matches Drizzle's default numeric mapping and avoids float drift. Rejected: numeric-as-number mode, integer minor units in the DB (spec requires numeric).
5. **User seed skips existing users** — idempotent and avoids silently resetting passwords. Rejected: upsert that overwrites hashes on every run.
6. **Sample seed is separate** — production seed and local fixtures have different safety rules. Rejected: one seed script with branching.
7. **Password rotation in the DB workspace** — reuses argon2 and DB access; API delegates. Rejected: duplicating hashing/DB code in the API.
8. **Rotation revokes sessions** — a password change should cut existing access. Rejected: leaving sessions alive.
9. **Separate `smartcanteen_test`** with a `_test` guard and serial execution — safe, simple, no Testcontainers dependency. Rejected: truncating the dev DB or parallel test workers.
10. **No `SESSION_SECRET`** — opaque tokens need no signing key; SHA-256 is the approved scheme. Rejected: HMAC pepper, which would change the spec.
11. **Forward-only migrations** — matches the ECS one-off task model and avoids down-migration risk. Rejected: reversible migrations.
12. **Vitest in the DB workspace** — schema/seed tests live beside the code. Rejected: pushing all DB tests into the API workspace.

## Risks

- Existing Docker volume: test DB creation is handled by the script, not the init SQL, so an existing volume is fine.
- `CREATE DATABASE` requires elevated privileges; local Docker and the CI service user have them. RDS migrations do not create databases.
- `CREATE EXTENSION citext` on RDS requires the master user or `rds_superuser`; Phase 6 must use appropriate credentials.
- Custom migration journal entries must be generated with drizzle-kit, not hand-edited, or the production migrator will skip them.
- Trigger/function migration is hand-written SQL; it will be verified against Docker with `\d+` and an update test.
- Argon2 native binaries must be available in the runtime image; `@node-rs/argon2` ships prebuilt binaries, and Phase 5 will verify the API image.
- Tests run serially against one database; slower but deterministic. A future CI matrix could shard by database name suffix.
- `npm run check` will fail if Docker/test DB is unavailable; that is intentional for the end-of-phase gate.
- Placeholder detection could reject an unusual production password containing a placeholder word; the error message will tell the operator which variable failed.
- The API's `dev` script will need `@smartcanteen/db` built before importing it in Phase 2; Phase 2 will address the dev build order.

## How I addressed the feedback

### 1. [Must fix] TLS to the database

- Added `DATABASE_SSL` (`off` | `require` | `verify`) and `DATABASE_SSL_CA_FILE` to env validation.
- `db/src/client.ts` is the single TLS implementation. It:
  - Sets `off` by default when `NODE_ENV` is not `production`, and `verify` by default when it is `production`.
  - Fails when `NODE_ENV=production` and `DATABASE_SSL=off`.
  - Builds the `ssl` option explicitly: `false` for `off`; `{ rejectUnauthorized: false }` for `require`; `{ ca: <file contents>, rejectUnauthorized: true }` for `verify` (Node verifies the hostname when `rejectUnauthorized` is true).
  - Requires `DATABASE_SSL_CA_FILE` for `verify` and fails clearly if it is missing or unreadable.
  - Strips `sslmode` from `DATABASE_URL` before passing it to `pg`, so URL parsing cannot silently override the explicit `ssl` option.
- `migrate.ts`, `seed.ts`, `seed-sample-items.ts`, `set-password.ts` and the future API pool all use this shared resolver. Phase 2's API DB factory will call `createPool`/`createDb` from this module; Phase 1 already validates the same production TLS rules in `api/src/env.ts`.
- Documented in `docs/SPEC.md` and `README.md`; added the variables to `.env.example`.

### 2. [Must fix] Production migrator proof
